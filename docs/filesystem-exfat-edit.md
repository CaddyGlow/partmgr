# Recoverable exFAT file and namespace editing

`fs_exfat_edit::ExfatEditor` owns a bounded filesystem region in exclusive `Storage` and a separate external undo journal. Opening requires a complete clean exFAT allocation audit performed through the currently owned target. The caller must establish exclusive access and verify that the journal is physically disjoint from the target; distinct Rust objects cannot prove either property. Bindings identify the actual volume, selected region and exclusive session, not merely its length.

The supported profile is revision 1.00 with one FAT and one allocation bitmap, checked native entry sets and full on-volume up-case comparisons. Dirty, media-failure, unknown-flag and TexFAT volumes are rejected. ClearToZero is bit 3, mask `0x8`: this write profile explicitly rejects it when set, rather than clearing it and claiming byte-identical rollback. Read-only files cannot be opened for editing. Unsupported benign allocation extensions remain explicit failures. File creation, directory creation, rename, move and deletion are supported under the same session fence. Volume resizing, overwrite-on-rename, recursive deletion, TexFAT and vendor allocation extensions remain unsupported.

The mutable target never implements immutable `ReadAt`. A borrowed `ExfatDecoder<&dyn Storage>` uses the same boot, FAT, bitmap, up-case, native directory and file-map validation as the immutable public wrappers. Source-independent extent indexes retain their resource leases. Files carry the editor scope and generation; any transaction attempt invalidates prior handles and batches. The caller supplies exact UTF-16 path components, including unpaired surrogates. Directory-set locations are retained individually, so sets crossing fragmented directory clusters are updated correctly.

`plan_replace` replaces a positional range within an existing logical file. If a write advances ValidDataLength, it first initializes the gap from the previous valid prefix with zeros, then writes the replacement. Only after those bytes are flushed and verified does it publish the new initialized prefix and recomputed entry-set checksum. Reads retain native zero semantics beyond ValidDataLength.

`plan_resize` extends with zero bytes or truncates. Extension chooses clusters exclusively from the retained same-session clean audit, initializes newly allocated clusters including their physical tails, and zeroes any existing uninitialized gap. A contiguous stream may remain NoFatChain; fragmentation produces checked FAT links for its complete allocation and publishes the corresponding stream flags. Truncation publishes the shorter native file set before releasing ownership, updates applicable FAT links, then clears bitmap bits. Empty streams use FirstCluster zero and the native empty-stream flags. Released data bytes are retained; future allocations are initialized before publication. The main PercentInUse is reconciled with the audited allocation count. Native names, timestamps, attributes and unrelated reserved bytes are preserved; no current timestamp is invented.

`open_directory` resolves exact native components and returns a generation-bound directory handle; an empty path selects the implicit root. `plan_create_file` initializes the supplied bounded payload and all physical allocation tails; `plan_create_directory` initializes an empty native directory without invented dot entries. Both require `ExfatCreateMetadata`, an exact caller-supplied primary-entry template with zero type/count/checksum and reserved fields, matching file/directory attributes and valid native timestamps. `epoch_1980` is an explicit fixed UTC timestamp choice, not a clock lookup. Creation does not infer metadata from a host file. Native UTF-16 names are retained exactly, including unpaired surrogates, and collisions use the entire checked on-volume up-case table.

`plan_rename` accepts source and destination directory handles and exact native names. It supports both in-place rename and entry-set relocation, preserving existing timestamps, attributes, allocation, initialized prefix and unrelated native fields while rebuilding name slots, NameHash and SetChecksum. Moving a directory into itself or a descendant is rejected using the validated ancestor allocations. No destination overwrite is implicit. `plan_delete` unlinks a file or an empty directory before releasing its verified owned FAT entries and allocation bitmap bits. Nonempty and read-only objects are rejected; directory allocations are not shrunk merely because an entry was removed.

Parent growth initializes new clusters before publishing FAT links and bitmap ownership. Root growth extends the checked FAT chain. Subdirectory growth updates its owner entry set, DataLength, ValidDataLength, NoFatChain semantics and checksum; fragmented growth converts the complete former contiguous allocation to FAT links. New entry sets may straddle old and new directory clusters. Entry bytes inside a newly allocated parent cluster are staged with that cluster's initialization, while existing slot publication follows allocation metadata. This keeps final undo patches disjoint. Relocation publishes the destination before unlinking the original under the durable dirty fence; the final complete audit must see a single owner before the clean flag can be published. `namespace_report` records the operation, exact new native name, new/released clusters, parent growth and preservation policy.

Namespace planning additionally bounds and reserves directory slots, native entry copies, allocation indexes and bitmap edits. Initialized object and parent bytes must jointly fit the affected-byte cap before proportional buffers are allocated. Names, slot scans, allocation searches and chain publication count against planning work. Newly grown parent buffers move into the final patch set rather than retaining an uncharged duplicate. Any transaction attempt invalidates directory handles as well as file handles and batches.

Every batch exposes disjoint final byte patches, named execution stages, affected-byte counts, and intermediate/final main volume flags. The external journal saves and verifies original and final bytes, then durably publishes Prepared before any target write. The editor's first authorized target write sets VolumeDirty and flushes and reads it back. Each subsequent stage is flushed and verified before the next. The final stage runs a complete structural audit while the actual target is still dirty, using a borrowed view substituting only the intended clean flag value. It clears the dirty flag only after that audit and all allocation, payload and native metadata publication checks succeed. Backup status fields remain stale as permitted by the native format; the authoritative main status is updated. Journal Committed is published only after final target verification.

Recovery requires the caller-verified persisted binding. It validates the saved body and supported flag framing before target mutation. The first restoration maintains a durable dirty fence. Restoration defers the low-offset clean flags patch, despite the journal's physical sorting. It flushes and verifies all restored payload and metadata bytes, then runs a complete audit through a borrowed storage view which substitutes only the journal's saved clean flag value. The actual target stays dirty throughout this audit. Only after that audit succeeds does recovery restore and flush the actual clean flags. The journal's rollback terminal marker follows target verification. An interrupted rollback leaves Prepared and can be restarted; a malformed or unrelated journal cannot confer editing authority. A failed journal publication proven by the continuing owner to have attempted no target write can be reset and reaudited without inferring that proof from filesystem cleanliness.

`ExfatEditLimits` bounds decoder/audit work, affected bytes, planning visits, journal patches and encoded journal bytes. Reservations precede proportional allocations; retained handles, batches, audit reports and undo plans keep their leases. Short writes are supported. Cancellation, backend failures, stale metadata, changed target length and exhausted limits are explicit failures. A failed transaction gates all subsequent access with NeedsRecovery. Releasing the stores preserves that explicit obligation; it does not complete recovery. Durability depends on the supplied `Storage::flush` implementation and the caller's continued exclusive access.

Independent tests author exFAT bytes without the production builder. They cover native UTF-16 names, contiguous and fragmented files, poisoned uninitialized tails, replacement, allocation conversion, truncation, empty files, generation invalidation, bounds, cancellation, refunds, and preserved image framing. Failure models inject torn writes and failed barriers at every transaction step for growth and truncation, retain or discard volatile bytes, reopen persisted journals, and interrupt every rollback write/barrier. Flush observations assert that rollback publishes clean flags only with the complete original image restored.

The explicitly enabled native gate formats a fresh 64 MiB volume using exfatprogs, inserts an independently authored regular file, edits it inside an image with an 8192-byte trailing frame and a 4096-byte prefix, and compares final framing and full payload with `fsck.exfat -n` and TSK `fls`/`icat`. It retains tool versions and executable hashes, source hashes, commands, stdout/stderr and unchanged hashes around read-only validation. Missing tools fail when enabled. This gate demonstrates the exercised profile and host durability calls; failure-model tests, rather than the host run, establish the tested restart behavior.

```sh
PARTMGR_EXFAT_EDIT_EVIDENCE=/data/cache/partmgr-exfat-edit-new \
  cargo test --locked --test fs_exfat_edit native_exfatprogs_tsk_editing -- --ignored --nocapture
```

Ordering and flag semantics follow the primary [Microsoft exFAT specification, sections 3.1.13, 3.2, 7.6 and 8.1](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification). External undo strengthens recovery for the declared profile; it does not make individual native sector writes atomic or supply a snapshot, physical exclusivity or repair authority for an unrelated image.

The range/resize native receipt refreshed against the additive namespace source is `/data/cache/partmgr-exfat-edit-native-20261008-generation-v6/receipt.txt` (the earlier v4 receipt is historical). It records the 131,089-byte initial file, a 333-byte replacement, zero extension to 140,000 bytes and truncation to 20,000 bytes, with full editor/TSK payload agreement, clean fsck validation, unchanged prefix/tail and read-only validator hashes, and complete lease refunds.

The namespace fixtures independently author native boot regions, custom up-case data, allocation bitmaps, FAT chains and entry sets. They exercise root and subdirectory growth, fragmented creation and zeroed tails, exact surrogate names, in-place rename and relocation, moves, cycle and collision rejection, empty-directory deletion, caller metadata rejection, cancellation, resource refunds and stale handles. Torn-write and failed-barrier injection covers every commit step for creation, relocation and deletion with retained/discarded volatile bytes. Interrupted namespace rollback is restarted after each modeled failure, including successful short writes, and clean rollback flushes are accepted only when the original framed image is restored.

The namespace native gate starts with an unmodified exfatprogs 64 MiB volume, creates 32 long-name files in the root and 20 in a subdirectory, and forces both directory allocations to grow. It moves a file under an exact Greek name, performs in-place rename, deletes a regular file and an empty directory, and rejects deletion of a nonempty directory. Independent `fsck.exfat -n`, recursive TSK `fls` and full `icat` payload checks validate all 51 retained files. The framed image, original mkfs image and validator image are hashed before and after read-only validation. The enabled gate requires all tools and a fresh evidence directory; it never silently skips missing dependencies.

```sh
PARTMGR_EXFAT_NAMESPACE_EVIDENCE=/data/cache/partmgr-exfat-namespace-new \
  cargo test --locked --test fs_exfat_edit_namespace native_exfatprogs_tsk_namespace -- --ignored --nocapture
```

Namespace rules use the primary [Microsoft exFAT specification, sections 6, 7.4, 7.6, 7.7 and 8.1](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification). Native host validation demonstrates the exercised format profile; it does not establish firmware behavior or hardware power-loss durability beyond the declared storage barrier contract. The exact-source namespace receipt is `/data/cache/partmgr-exfat-namespace-native-20261008-generation-v4/receipt.txt`: status passed, two root growth clusters, one subdirectory growth cluster, 51 matching payloads, unchanged framing/validator hashes and complete refunds.
