# Deterministic offline JFFS2 new-image builder

An additive [compressed authoring profile](filesystem-jffs2-builder-compression.md) selects RTIME or ZLIB without changing these options or the default entry point. `Jffs2BuildPlan::from_tree` authors `jffs2-direct-logical-nor-tree-none-zero-v1` directly from an `Arc<dyn TreeSource>`. It does not invoke `mkfs.jffs2` to implement authoring. The destination is an exclusively owned, unpublished fixed-size regular image accessed through `Storage`. Publication and physical flash programming are caller responsibilities. This implementation is not an existing-image editor, append/recovery protocol, garbage collector, or physical NAND/OOB/ECC writer.

Options explicitly declare endian, `FlashGeometry`, name treatment, source metadata replacement, and optional native ZERO nodes. Geometry accepts logical NOR, erased `0xff`, clear-bits programming, power-of-two erase blocks of at least 4096 bytes, and declared program alignment of 1, 2, or 4. Output length consists of whole erase blocks. Nodes are four-byte aligned and cannot cross erase boundaries. Each erase block begins with a canonical 12-byte cleanmarker; every other unused byte and alignment/tail byte is initialized to `0xff`. Even unused blocks receive cleanmarkers and therefore are not reported as entirely erased free blocks by the conservative reader audit.

The layout/CRC reference is Linux's [JFFS2 native node definition](https://raw.githubusercontent.com/torvalds/linux/master/include/uapi/linux/jffs2.h), together with its [scan rules](https://raw.githubusercontent.com/torvalds/linux/master/fs/jffs2/scan.c) and [version reconstruction](https://raw.githubusercontent.com/torvalds/linux/master/fs/jffs2/readinode.c). The builder emits inode, dirent and cleanmarker nodes with native-endian fields and initial-zero reflected IEEE CRC32 header/node/data/name checksums. All authored inode versions are strictly increasing from one; directory name versions are deterministic per-parent ordinals from one. Root inode 1 is authored explicitly. Regular files use bounded, increasing-offset data nodes; zero-length files receive one metadata node. Directories have zero data length. Symlinks use one complete uncompressed node, retain exact target bytes, and are never followed.

Inventory preserves hardlinks by equal complete source-scoped object identities. Directory aliases/cycles, conflicting identity types, special objects, malformed pagination, sibling name collisions, missing or additional regular streams, and extra directory/symlink streams fail preflight. A retained identity's native key is bounded to 256 bytes in this profile. Unique objects receive deterministic native inode numbers as breadth-first inventory discovers sorted native sibling names. Source pagination and entry order do not change output bytes. Data payloads remain deferred `Arc<dyn FileRead>` handles. No extracted host tree or whole file/image buffer is required by production code.

`NativeBytesOnly` preserves exact byte names and rejects UTF-16. `Utf16ToUtf8` explicitly converts well-formed UTF-16 names while preserving input byte names. Converted siblings are checked for exact byte collisions, without case folding. Destination names are 1–254 bytes and exclude NUL, slash, dot and dot-dot. Symlink targets must already be native bytes, contain no NUL, and be 1–254 bytes; they receive no implicit path or encoding conversion. Non-UTF-8 native names remain possible, though the native extraction tool used by this gate cannot validate them.

`ReplaceWithDefaults` explicitly authorizes replacing source UID/GID, permissions, access/modification/change time, flags, security, timestamps and opaque attributes. Callers provide native 16-bit UID/GID, regular/directory/symlink permission bits through 0777, and unsigned Unix seconds. Symlink targets are retained. `RequirePreservation` fails before output: arbitrary source metadata preservation is unsupported. Reports identify authored defaults, name policy, converted-name count, transformed-object count, preserved additional hardlink names and actual source stability. They explicitly report that source sparse allocation is transformed into logical bytes or ZERO nodes.

All logical data is read through the source stream's defined zero semantics. Optional ZERO encoding recognizes complete all-zero regular data chunks; a ZERO node stores no data and carries its logical data size. Layout reserves the worst-case NONE node span even when ZERO is selected, leaving the remainder erased. This keeps capacity preflight independent of deferred payload bytes. Logical content is preserved; source allocation shape is not.

`Jffs2BuildLimits` independently bound objects, entries, converted name/symlink bytes, records, image length, depth, inventory/layout work, data-node bytes and output scratch. Data nodes are 128–32768 bytes and must fit with their header and a cleanmarker within one declared erase block. Streaming/readback scratch is 512–65536 bytes. Complete geometry, connectivity, stream profile and worst-case space checks precede mutation. Fallible metadata/map allocations retain shared reservations; planning retains the original cancellation context and source tree/stream handles. Peak inventory reservations are conservative functions of explicit caps, while record layout is charged from the checked actual record count.

Source identity/length and tree revalidation run before and after streaming, during each file-node read, and during full regeneration. Symlink target metadata is revalidated against retained exact bytes. Both planning and per-operation cancellation contexts remain active. These checks respect the source's declared stability; they do not establish snapshot isolation or detect all same-size concurrent byte changes.

Emission initializes every output byte, supports short writes, performs one explicit final flush, then regenerates and compares every image byte and whole-image SHA256. Regeneration rereads deferred payloads within bounded scratch. `Jffs2BuildFailure` retains the causal domain/I/O error and separately reports whether mutation was attempted, explicitly accepted bytes, verified bytes and whether flush completed. A write error may hide partial changes even when accepted bytes are zero. A flush error is uncertain durability; a later readback error does not undo a successful flush. The destination remains unpublished on failure. Actual flush/readback behavior is not evidence of physical power-loss atomicity.

Portable tests exercise both byte orders and node encodings, source-order determinism, exact erase-boundary endings, successful UTF-16 conversion and non-UTF-8 byte preservation, low-memory preflight refund, a 90013-byte payload larger than the 4096-byte work buffer, sparse/zero content, hardlinks, symlinks, interpreted default metadata, space/record caps, conversion collisions, stream/preservation rejection, cancellation, stale identity/size, causal payload failures, modeled partial writes, flush failure and readback corruption.

The explicitly ignored native gate requires mtd-utils and independent Jefferson extraction. Enabling it without its tools or fresh evidence location fails:

```sh
JFFS2_TOOLS=/path/to/mtd-utils/bin \
JFFS2_EXTRACTOR=/path/to/jefferson \
JFFS2_BUILD_EVIDENCE=/fresh/durable/directory \
cargo test --all-features --locked --test fs_jffs2_builder -- --ignored --nocapture
```

An independent mtd-utils NONE-node source image is read through `RawDisk` → `Jffs2Volume` → `Jffs2TreeSource`; authoring never consumes its extracted host files. Each output is emitted through locked `FileStorage` and completes one actual backend flush before independent inspection. The gate authors eight 256 KiB images: LE/BE × NONE/ZERO × two opposite source enumeration orders, with 64 KiB erase blocks and explicit metadata defaults. Independent mtd-utils 2.3.1 `jffs2dump` validates authored node/CRC structure. Jefferson 0.4.8 independently extracts and hashes the 90013-byte payload and verifies the unfollowed symlink target. Matching complete image hashes prove repeat/order determinism, and each output is reopened through the checked reader and complete namespace audit. Tool versions/binary/extractor-source hashes, exact argv, source and output hashes, maximum source read size, flush count and outcomes are retained in `jffs2-direct-tree-builder-v1.txt`.

`jffs2dump` independently confirms that both hardlink names reference the same native inode. Jefferson retains one dirent per inode, so its extraction alone cannot prove both names; the separate common-reader/tree checks also verify shared identities. It cannot certify non-UTF-8 native names. `JFFS2_EXTRACTOR_PYTHON` can explicitly select the extractor interpreter when its launcher lacks a simple absolute shebang. `JFFS2_SPEC_ARCHIVE` retains the consulted primary references and hashes. No native kernel mount, device programming, erase-cycle behavior, recovery after interruption, append or GC correctness is claimed. Those remain subsequent milestones.
